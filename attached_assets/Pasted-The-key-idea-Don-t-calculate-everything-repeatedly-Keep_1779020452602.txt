The key idea:

Don’t calculate everything repeatedly.
Keep live state in memory and update incrementally.

That is how you scale to many symbols.

Correct architecture for MANY symbols
Core idea

You maintain:

ONE live state object per symbol

Example:

{
  BTCUSDT: {
    ema100: 104200,
    ema200: 103800,
    previousClose: 104100,
    currentClose: 104500,
    status: "ABOVE_EMA100",
    lastSignal: "CROSS_UP_100"
  },

  ETHUSDT: {
    ...
  }
}

This stays in RAM memory.

That’s the secret.

IMPORTANT:
You DO NOT recalculate from candle history every time

Wrong approach:

for every update:
   fetch candles
   recalculate EMA100

That dies instantly at scale.

Correct approach

You calculate EMA incrementally.

Each new candle only updates:

newEMA

using previous EMA.

This is O(1) per update.

VERY fast.

Backend design
Layer 1 — Symbol Registry

Store all tracked symbols:

const symbols = [
  "BTCUSDT",
  "ETHUSDT",
  "SOLUSDT"
]

Maybe:

all USDT pairs
user-selected pairs
Layer 2 — Historical Bootstrap

When server starts:

Fetch 200 candles ONCE per symbol

Needed for:

EMA100
EMA200

Then calculate initial EMA.

After that:

no more historical recalculation.
Layer 3 — WebSocket Manager

Connect to Binance stream.

You can subscribe in batches.

Example:

btcusdt@kline_1m
ethusdt@kline_1m
solusdt@kline_1m

Binance pushes updates continuously.

Layer 4 — In-Memory Symbol Engine

Most important part.

Use:

Map()

Example:

const store = new Map();

Each symbol:

store.set("BTCUSDT", {
   ema100: 0,
   ema200: 0,
   previousClose: 0,
   currentClose: 0,
   signal: null,
   updatedAt: 0
});

This is EXTREMELY fast.

Layer 5 — Candle Processor

When Binance sends CLOSED candle:

x = true

Process:

1. get symbol state
2. update EMA100
3. update EMA200
4. compare previous/current
5. detect cross
6. update memory
7. emit frontend event
VERY IMPORTANT optimization

Process ONLY closed candles.

NOT every tick.

Reason:

tick updates are massive
candle close is enough for EMA signals

This massively reduces CPU usage.

Example flow for 500 symbols

Every minute:

500 closed candles arrive

For each symbol:

~5 math operations
~2 comparisons
~1 memory update

That is very lightweight.

A normal VPS can handle this.

Efficient EMA update

Instead of recalculating 100 candles:

newEMA =
(close - previousEMA) * multiplier
+ previousEMA

Only one formula.

Fast.

PROCESS 1 — Scanner Engine

Responsible for:

Binance sockets
EMA calculations
signal detection

This should be isolated.

PROCESS 2 — API Server

Handles:

frontend requests
symbol lists
filters
users
PROCESS 3 — WebSocket Push Server

Sends frontend updates.

Could be merged initially.

Express

500+ symbols
Scaling later

Split workers

Worker 1:
BTC → H

Even bigger scaling

Use:

Memory design

Store ONLY latest state.

Do NOT store huge candle history in RAM.

Example:

{
  ema100,
  ema200,
  previousClose,
  currentClose,
  lastSignal
}

That’s enough.

Database usage

Database is ONLY for:

users
watchlists
saved alerts
historical signals

NOT live calculations.

Key professional insight

Professional scanners are basically:

continuous state machines

Each symbol has:

current state
previous state

Every new candle:

transition state
detect event

That’s all.

Binance WebSocket
        ↓
